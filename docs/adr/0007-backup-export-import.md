# ADR 0007: Backups use the online API; import merges on a stable `uid`

- **Status:** Accepted
- **Date:** 2026-09-28
- **Affects:** `DEP-07`, `DEP-08`, `DEP-09`, `DEP-11`, `NFR-REL-01`, `NFR-REL-03`,
  `NFR-DATA-01`, `DATA-13`, `Q14`, `Q15`; releases 0.1.0, 0.9.0

## Context

`DEP-07` requires a daily automatic backup into `./backups` keeping the last 14 copies,
plus a manual Backup now button, with the count configurable. `NFR-REL-01` forbids losing
committed data on a stop, crash or power loss, and requires write-ahead logging. `DEP-09`
requires migrations to take a backup first and never delete user data. `NFR-REL-03`
requires backups to be verifiable: the restore procedure must be documented **and tested**.
`DEP-08` requires export as JSON, plus CSV for time entries, and the ability to import a
previous export. `DATA-13` requires import to only add or merge, never overwrite or remove.
`NFR-DATA-01` requires open formats so the data is never locked in.

Two traps and one gap sit inside these requirements.

**The copy trap (S8).** With WAL mode on, the database is three files: `pdm.db`,
`pdm.db-wal` and `pdm.db-shm`. Copying `pdm.db` while a write is in flight produces a file
that is internally consistent as of some earlier checkpoint but silently missing recent
commits, and copying it while the WAL is mid-transaction can produce a file that will not
open at all. The obvious implementation — `cp pdm.db backups/$(date)` from a cron-like job
— is the one that loses data.

**The retention tension (Q14).** `DEP-07` says keep 14 copies, which means deleting old
files. That is a delete. `DATA-09` forbids deleting *user data* and `Q14` asks explicitly
whether rotating backup copies is acceptable; the SRS's own answer is yes, because only
copies rotate and the live database is never touched.

**The merge gap (S5).** `DATA-13` says import merges, but the SRS defines no cross-instance
identity. Without a stable key, "merge" is either "insert everything and create
duplicates" or "match on name", which is wrong — the user may legitimately have two tasks
called *Fix login*, and renaming a task should not turn an import into a duplicate.

## Decision

**Every user-data table gets `uid TEXT NOT NULL UNIQUE`** holding a UUIDv7, generated by
the database default on insert. UUIDv7 because it is time-ordered, so inserts stay
append-ordered on the index and the primary sort key remains the integer id. `uid` is
assigned once and never changed. `activity_log`, `settings`, `schema_migrations` —
now `knex_migrations`, per ADR 0012 — `mcp_audit_log` and `reminder_deliveries` are not
exported, because they are either local bookkeeping or per-instance state.

**Backups use SQLite's online backup API, never `cp`.** `better-sqlite3` exposes
`db.backup(destination)`, which takes a consistent snapshot while writes continue. A
safer, cheaper alternative for a small database is `VACUUM INTO 'path'`, which writes a
freshly compacted copy directly to the target file; both are acceptable, and `VACUUM INTO`
is the default because the output is a single clean file with no WAL.

**A backup is a complete database file**, written to
`./backups/pdm-YYYY-MM-DDTHH-mm-ss.db`, then verified: the file is reopened, `PRAGMA
quick_check` must return `ok`, and the row counts of the six largest tables are recorded
in a sidecar `.json`. A backup that fails verification is reported, not silently kept.

**Retention deletes only files matching the backup naming pattern inside
`./backups`.** This is the answer to `Q14`: the code refuses to delete any file that does
not match `pdm-<timestamp>.db` or its `.json` sidecar, so the backup directory can never
become a general-purpose delete path for anything the user put there.

**Restore is documented as a manual, tested procedure** (`NFR-REL-03`):

1. `docker compose down`
2. Copy the chosen backup over `./data/pdm.db` and remove any stale `pdm.db-wal` and
   `pdm.db-shm`
3. `docker compose up -d`
4. Open the app, check `/health`, and confirm totals on the Day log and Reports

Step 2's removal of the stale WAL files is essential and is the step people skip. 0.9.0's
exit test performs this drill on a **copy** of the real data, and the result is recorded in
the release notes and in `README.md` (see `OQ-4`).

**Migration backups use the same mechanism**, into `./backups/migrations/`, with the
migration name and timestamp, before the migration runs. If the migration fails, the
container aborts its boot and says which file to restore (`DEP-09`).

**Export produces three files**, written to `./backups/exports/`:

| File | Content |
| --- | --- |
| `pdm-export-<timestamp>.json` | Every user-data table, keyed by table name, rows as objects, each with its `uid` |
| `pdm-entries-<timestamp>.csv` | Time entries flattened to columns, for a spreadsheet |
| `pdm-export-<timestamp>.json.sha256` | Checksum, so an import can refuse a truncated file |

JSON is the complete, restorable form. CSV is a convenience for analysis and is
explicitly **not** an import source, because a CSV has no `uid` and cannot satisfy
`DATA-13` (`NFR-DATA-01`).

**Import is insert-only, keyed on `uid`.** Every insert is
`INSERT ... ON CONFLICT(uid) DO NOTHING`, wrapped in one transaction, with a pre-check that
refuses a file whose checksum does not match. Consequences:

- Importing the same file twice changes nothing the second time — no duplicates, which is
  also what `MCP-27` requires of the assistant's create tools.
- Importing into a populated database adds only records the instance has never seen.
- Import never updates an existing record and never removes one, exactly as `DATA-13` and
  `BR-13` require.

**Import preserves time exactly.** Timestamps are exported as epoch milliseconds, the same
representation they are stored in, so no timezone conversion happens in the file.

**Import cannot write into a running timer or a pending closure.** `MCP-16` and `MCP-15`
keep time tracking and task closure in the user's hands; an imported open `time_entry` would
be a second source of truth, so rows with `ended_at IS NULL` are skipped and reported. This
keeps the ADR 0003 invariant of at most one open entry intact.

**The export is also the migration path to a future multi-user version.** Because every
record carries a `uid` and the format is documented JSON, version 2 can import a version 1
database without guessing.

## Consequences

Easy: backups are consistent by construction, whether or not the app is busy. Restore is
four commands a user can follow. Import is genuinely safe to run repeatedly, which removes
the fear that usually stops people from using an import at all. The data is in open
formats that outlive this app.

Hard: `uid` is on every user-data table from 0.2.0 and cannot be added later without
touching every table and every export. This is the main reason 0.2.0 writes the full schema
once.

Hard: a backup is a whole database file, so 14 copies of a growing database consume 14
times the database size. On the expected volume this is tens of megabytes per copy. A
compressed backup is not implemented, because the restore procedure is the thing that
actually matters and simplicity is what makes it reliable.

Accepted: a nightly backup cannot protect against a failure in the last 24 hours. Hourly
backups are the obvious next step and were not asked for; the number is a setting, so
adding it later needs no schema change.

## Alternatives considered

**Copying the file with `cp` on a schedule.** Rejected: unsafe with WAL, and it is the
mistake most likely to be made by anyone maintaining this later. A comment in the backup
module says so.

**Copying `pdm.db`, `pdm.db-wal` and `pdm.db-shm` together.** Safer than one file, but the
result needs a checkpoint before it is usable and it is easy to end up with a mismatched
set of three. A single consistent snapshot is simpler to reason about and to restore.

**SQLite's `.backup` CLI inside the container.** Equivalent result, but it needs the CLI in
the runtime image, a subprocess, and separate argument handling. The library call is one
line and stays in-process.

**Export-only, with no database-file backup.** Rejected: `DEP-07` and `NFR-REL-03` require
an automatic backup and a tested restore, and an export is a lossy way to satisfy that.

**Import that updates on `uid` match.** Tempting, and it would resolve naming drift. Rejected
because `DATA-13` says import must never overwrite, and an import that can rewrite a closure
record or a lagging reason undermines the append-only guarantee of `BR-10`.

**Matching import on task name within a project instead of `uid`.** Rejected: two identical
task names are legal, and a renamed task would be re-imported as a duplicate.
