## Where this release actually stands

**The schema is done, and so is the foundation layer the schema was missing.**

**Schema:** one migration, `0001_initial_schema.js` — all 15 tables, `uid` and
`archived_at` on every user-data table but two, 14 `BEFORE DELETE` triggers, the
3-link trigger, the one-open-timer partial unique index and the closure check
constraint. `apps/api/src/db/schema.test.ts` (60 tests) asserts each against a real
database, including that this single file really does create all 15 tables and
all 14 triggers. The three files it replaced (`0001_settings`, `0002_data_model`,
`0003_invariants`) carried stale version numbers in their own comments; they were
consolidated on 2026-09-29 because nothing was released yet, which is the cheapest
moment to do it. See `D-26`.

**Foundation (this session):** the three layers every later service writes through
now exist, with the rules they are supposed to enforce:

- `apps/api/src/lib/errors.ts` — the typed `AppError` a service throws and one
  code-to-status map, so a refusal keeps its identity instead of being guessed from
  a message. `validationDetails` turns a Zod failure into `details.issues[]` with a
  dotted field path, and deliberately does not echo the submitted value.
- `apps/api/src/middleware/` — `request-id.ts`, `principal.ts` (the MCP token
  arrives in 0.10.0, the seam is built now), `error.ts` (the envelope, extracted
  from `server.ts`) and `services.ts` (one service instance per process, so a
  handler cannot open a second pool and a second transaction).
- `apps/api/src/routes/table.ts` — every route is **declared** with its
  capabilities, `DELETE` is unrepresentable, an empty capability set is refused
  rather than allowed, and an `onReady` hook **refuses to boot** if any route was
  registered outside the table.
- `apps/api/src/repositories/activity-log.repository.ts` and
  `apps/api/src/services/activity-log.service.ts` — the first repository and the
  first service, and the first `describe` block that names a criterion rather than a
  function.
- `packages/shared/src/uid.ts` — UUIDv7 through the `nowMs()` seam, which nothing
  previously generated.

Done since that paragraph was written: the project repository, service, declared
routes and `/projects` screen, including archive/restore and “Show archived” —
and now the same for task core: repository with the project-aware archive
filter, service with status moves and `started_at`, declared routes, and the
`/tasks` screen with filters, sorting and the “No project” bucket. `ended` is
not writable anywhere in this slice, by type and by test.
Done since: acceptance criteria with the same shape — repository, service,
declared routes, and a detail-page section kept visibly separate from todos
(`FR-AC-03`): no tick box anywhere near a condition. Met/not-met is decided at
closure in 0.5.0, never here.
Done since: reference materials — repository, service, declared routes, and a
detail-page section with typed kinds. Nothing here checks the task's state on
read and nothing cascades, so a reference outlives its task by doing nothing.
An empty URL field means `null`, never a blank link.
Not started: `apps/api/src/views/`, tags (the last domain), and tag UI. The
timer's task picker and per-row Start button wait for 0.3.0, which is what they
start.

**Consequence for the plan:** the exit test still cannot be run. It creates
projects and tasks through the UI, and there is no UI for either. The release
ladder stays blocked at 0.2.0 until the entity services and the UI land.

## Goal

The whole schema exists, nothing can be deleted, and projects, tasks and tags are
usable.

This release has no timer and no closure gate. It has the ground they stand on:
fifteen tables, the constraints that make them trustworthy, and the first real
service functions. A schema mistake here is discovered by every later release, and
a schema change later is a migration against real data, so this is the cheapest
moment in the whole ladder to get the shape right — which is exactly why the full
model lands here rather than incrementally.

## In scope

- All 15 entities of SRS §9.1, with `uid`, `archived_at`, `created_at`, `updated_at`
- Migrations for the schema, the views, the triggers and the indexes
- `BEFORE DELETE` triggers on 14 of the 15 user-data tables; `time_entry_tags`
  is exempt as a pure join (`DATA-10`)
- `CREATE UNIQUE INDEX … WHERE ended_at IS NULL` on `time_entries` (`DATA-02`)
- `BEFORE INSERT` trigger capping `task_links` at 3 per task (`DATA-01`, `BR-04`)
- `closure_records` check constraint: `result = 'not_fulfilled'` requires a
  non-empty `lagging_reason` (`DATA-03`)
- `activity_log` written by the service layer on every change (`FR-STAT-05`)
- Project CRUD with archive and restore (`FR-PRJ-01`…`04`)
- Task CRUD with links, score, estimate, dates, status, todos, acceptance criteria
  and reference materials (`FR-TASK-01`…`09`, `FR-TODO-01/02`, `FR-AC-01/02`,
  `FR-REF-01/02`, `FR-TAG-01/02/05`)
- Task list with sort and filter (`FR-VIEW-01`, `FR-VIEW-03`)
- "Show archived" and Restore everywhere, with no Delete button anywhere
  (`UI-04`, `UI-17`, `DATA-11`)
- Form validation that preserves the typed value (`UI-08`)
- Capability classification on every route, so `MCP-14` has something to read
- Web UI for the above

## Out of scope

Timer, Day log, closure gate, calendar, reminders, search, reports, MCP. Time
entries exist as a table because the schema is written once; nothing writes one
until 0.3.0.

## Out-of-scope by decision

- **`drizzle-orm` is dropped, not wired up.** It was declared in `apps/api/package.json`
  since 0.1.0 with zero imports, and `AGENTS.md`, `docs/ROADMAP.md` and ADR 0009 all
  described it as the query layer — docs describing an architecture the code did not
  have. The owner dropped it on 2026-09-29; the query layer of this release is the
  Knex constructor below. This also closes the one Definition of Done box 0.1.0 left
  open.
- **The migration runner is Knex, not Umzug.** Owner decision 2026-09-29 (ADR 0012,
  superseding ADR 0009). Migrations are `NNNN_name.js` files run by Knex over its
  `knex_migrations` ledger; `schema_migrations` and the immutability checksum are
  gone, and the data-model SQL sits inside the migration files as byte-identical DDL
  rather than as separate `.sql` files. The wrapper keeps the pre-migration backup,
  restore-and-abort and contiguity checks. Acceptance criterion 14 below asserts the
  new ledger.
- **No upgrade path from 0.1.0, and none is planned.** A 0.1.0 `data/` directory is
  discarded and recreated, not migrated (`D-26`). This release previously claimed the
  upgrade path "was verified against a real data directory" — it had not been run at
  all, and running it showed a dead `schema_migrations` ledger surviving alongside
  `knex_migrations`. The claim is withdrawn rather than repaired. The migrator's
  contract *is* verified against a real data directory, including the failure path:
  a deliberately broken migration exits 1, names itself, restores its backup, rolls
  back, and `pdm` does not start.
- **No search.** `reference_materials` is a plain table here. FTS5 indexing is
  0.8.0 and gets its own migration, per ADR 0005.
- **URLs are versioned and split into two namespaces.** Owner decision 2026-09-29
  (ADR 0013). Every JSON route lives under `/api/v1`, every page and asset under
  `/ui/v1`, and only `/health`, `/ready` and `/` are unprefixed — `/` answering
  308 to `/ui/v1/tasks`. `/health` is unchanged, including the Docker health check
  that calls it, and `/ready` is new and unprefixed so a monitor does not have to
  know the deployed version. `RouteTable.declare` refuses a URL outside the scheme
  at boot, which is where criterion 11's refusal instinct comes from applied to
  routing. **No legacy aliases:** `/tasks` and `/api/tasks` are 404. The address
  bar now reads `http://127.0.0.1:9090/ui/v1/tasks`.

## Acceptance criteria

`[done]` verified against the code, `[half]` part of it is landed but the criterion
also needs behaviour that does not exist yet, `[todo]` not started. A criterion moves
to `[done]` only once its own assertion passes — see the coverage note under
criterion 14, which is what makes the count here trustworthy.

1. **[done]** Adding a 4th link to a task returns 422 with a clear message, and a direct SQL
   insert of a 4th link is rejected by a database trigger (`DATA-01`, `US-06`).
   The service refuses first with a message naming the limit of 3, then the
   trigger refuses for any writer that never calls the service. URLs must parse
   as absolute; positions are service-assigned slots 1–3, freed by archiving and
   re-taken on restore. Proven through `app.inject()` (`POST` returns the 422
   with “3” in the message) and against the real trigger.
2. **[done]** Every user-data table except one refuses `DELETE` at the database level,
   proven by a test that enumerates all of them and asserts on the count (`DATA-10`).
   **The count was wrong in this spec until 2026-09-29, and so is the one in
   `AGENTS.md`.** Measured against a real migrated database: **15 user-data
   tables, 14 of them carrying a `BEFORE DELETE` trigger.** The exemption is
   `time_entry_tags`, a pure join with no independent identity, plus the two
   `knex_migrations*` system tables. The old "13" counted neither `settings`
   (whose trigger arrived in migration 0002) nor the fact that one table is
   deliberately exempt. The test asserted 14 and its comment explained the
   arithmetic while the prose said 13 — **the test was right and the docs were
   wrong**, which is the whole argument for the label rule above.
3. **[done]** Archiving a project hides it and its tasks from pickers and default lists, keeps
   all data, and restoring brings everything back (`FR-PRJ-04`, `BR-16`, `US-07`).
   The task list reads the project's state rather than copying it: archiving a
   project hides its live tasks from default lists without touching them, and
   restoring brings them back. The task form's project picker offers live projects
   only. The one picker this does not cover is the timer's task picker, which
   arrives with the timer in 0.3.0.
4. **[done]** Archiving a tag hides it from pickers but leaves existing entries and per-tag
   totals unchanged (`FR-TAG-05`). The manager refuses duplicate live names,
   archive hides from default lists, restore refuses a name taken meanwhile —
   all naming the tag. The entries half is structural until 0.3.0: nothing in
   the tag service names `time_entry_tags`, so no archive can move a total.
5. **[half]** Archiving a todo keeps its time entries linked to it (`DATA-05`,
   `FR-PHASE-05`). **The schema assertion this claimed existed did not.** It now
   does: `schema.test.ts` archives a todo that has a real entry against it and
   asserts the entry survives, keeps its `todo_id` and `task_id`, and is _not_
   itself archived — because hiding the hours along with the phase would be a
   stored number quietly changing (`DATA-04`), and `DATA-12` exists because
   excluded time must be shown rather than silently dropped. Done since: the todo
   service with archive/restore, which never names `time_entries` — an archived
   todo keeps its links by construction, not by care. Still outstanding: 0.3.0's
   real entries through the API, which is the proof that survives contact with
   actual time tracking rather than with the schema alone.
6. **[todo]** Editing an Ended task is allowed and the change is recorded in history
   (`FR-TASK-12`, `FR-STAT-05`). Untestable until an ended task can exist, which
   waits for the closure service in 0.5.0. The task service already refuses to
   move an ended row, so the state this criterion edits cannot be produced yet.
7. **[done]** No API route accepts a delete of user data; a test scans the route table and
   fails on any `DELETE` method (`DATA-09`). `RouteTable.declare` throws on `DELETE`,
   so the route is never even recorded; `apps/api/src/routes/table.test.ts` (19 tests)
   asserts that, plus that an archive — a `PATCH` — is still allowed.
8. **[done]** A task may belong to no project and shows in a virtual "No project" bucket
   (`FR-PRJ-02`). `project_id` is nullable, `project_id=none` filters the list to
   the bucket, and the UI offers it as a filter and as a create/edit choice. "No
   project" is a real choice, never a magic number.
9. **[done]** Validation errors name the field and the typed value is preserved (`UI-08`).
   The **backend** half is done: `AppError` carries a code and a `details.issues[]`
   whose path is the dotted field name, an unparsed Zod failure from a handler is
   still a 422 rather than a 500, and the submitted value is deliberately **not**
   echoed back. The form half is done for every 0.2.0 screen — projects, tasks,
   todos, links, criteria, references, tags: a rejected save shows the field
   error and leaves every typed value in place. Later releases' forms repeat the
   pattern rather than completing it.
10. **[done]** Archived items appear in search-independent lists only when "Show archived" is
    on (`DATA-11`). Every list that exists honours it: projects, tasks, todos,
    links, criteria, references and tags all default archived rows out and take
    `include_archived`, each screen states the opt-in in words. The search
    clause waits for search itself in 0.8.0 — there is nothing to appear in yet.
11. **[done]** Every user-data table carries a unique `uid`, and every one except two
    carries `archived_at` (`DATA-13`). **The wording was wrong until 2026-09-29.**
    Measured against a real migrated database: 15 user-data tables, **14 with a
    `uid`** — `time_entry_tags` is exempt, a pure join with no identity of its own
    — and **13 with `archived_at`**, the second exemption being `activity_log`,
    which is append-only: a log entry that could be archived is a log entry that
    could be hidden. `AGENTS.md` claims five system tables are exempt from the
    no-delete triggers; only two exist so far, and those two are the Knex ledger,
    not user data. The migration count test asserts 14 and was correct.
12. **[done]** A route with no declared capability is refused, and a principal without the
    capability gets 403 — asserted through `app.inject()` with a principal that has
    no capabilities at all (`MCP-14`). Both halves are enforced rather than
    documented: `registerRoutes` installs a default-deny `onRequest` guard, a
    declaration with an empty capability set is refused at boot rather than allowed,
    and an `onReady` hook **throws** if any route exists that the table never saw, so
    a handler added straight to the app cannot ship unauthorised. 20 tests.
    Re-checked when the entity routes land, since each of them is a new declaration.
13. **[done]** The activity log records every status change with a before and after value
    (`FR-STAT-05`). Every reachable status change is logged as a diff in the same
    transaction, and `GET /api/v1/tasks/:id/history` reads it back newest-first for the
    detail page's history section — driven end to end against the live container
    for the exit test, two moves showing with before and after. "Every" still
    excludes `ended`, which nothing can write until the closure service in 0.5.0.
14. **[done]** `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:int` and `pnpm build`
    pass from a clean checkout, on a database created by the migrations alone.
15. **[done]** The URL scheme holds, and it is refused where a route enters the app
    (ADR 0013). `API_V1 = '/api/v1'`, `UI_V1 = '/ui/v1'` and the allowlist
    `['/health', '/ready', '/']` live in `packages/shared/src/http.ts`;
    `RouteTable.declare` throws on anything else at boot, so an unprefixed route
    cannot ship. The SPA fallback asks `isUiPath` — a positive question — rather
    than the old "is this under `/api`", which was why a mistyped `/tasks`
    returned the whole app shell with a 200 and now returns a 404 envelope.
    `/` answers 308 to `/ui/v1/tasks`, `/health` is byte-for-byte unchanged,
    `/ready` returns 503 on pending migrations where `/health` still returns 200.
    Two predicates rather than one, because a UI path may not be *declared* while
    it must still be *served*; that split was found by a test, not by foresight.
    Verified over HTTP against the rebuilt container, in both directions: all
    prefixes, all refused paths, an asset load, and a real create/archive cycle.
    22 new tests across 5 files.

## Exit test (owner, ~15 minutes)

1. `docker compose up -d --build --wait --wait-timeout 60` and confirm the app is healthy.
2. Open `http://127.0.0.1:9090/` and confirm the address bar ends up at
   `/ui/v1/tasks` and the page loads — including its assets, which now live under
   `/ui/v1/assets/`.
3. Open `http://127.0.0.1:9090/tasks` and confirm you get a JSON 404 envelope,
   **not** the app shell. Then try `/api/tasks` and `/ui` — all three 404.
4. `curl -i http://127.0.0.1:9090/ready` is 200, and
   `curl -i http://127.0.0.1:9090/health` is unchanged from before.
5. Create a project. Create three tasks in it, and one with no project.
6. Give a task three links. Try a fourth: it is refused with a message naming the
   limit.
7. Add a todo, two acceptance criteria and a reference material to one task.
8. Create two tags, apply one to a task's tags. **Half of this step waits for
   0.3.0:** tags attach to time entries, and nothing writes an entry until
   then. Creating the two tags works today; applying one does not exist yet.
9. Archive the project. Its tasks vanish from the default list; "Show archived"
   brings them back; Restore brings the project back.
10. Archive a tag. It disappears from the picker.
11. Change a task's status twice and open its history. Both changes are there, with
    before and after.
12. Search the whole app for a Delete button. There is none.
13. `docker compose logs pdm-migrate` shows the schema migrations applied in order.

## Risks

**Schema churn is cheapest now.** Every table created here is a table every later
release queries, and the alternative — adding `uid` and `archived_at` in a later
release — means touching every table, every export and every import at once
(ADR 0007). This is the release where a wrong column name is a rename rather than
a migration against real data.

**The 14 no-delete triggers can disagree with the application.** If a service
archives and a trigger also fires on delete, the two must not contradict each
other. The triggers are the last line of defence, not the mechanism, and the
enumeration test is what keeps the count honest.

**`FR-STAT-01` is a design constraint, not a test.** A task must never reach
`ended` by any route. That is only provable if exactly one function can set it, so
`ended` is not writable from a generic update path in this release even though
nothing can legitimately set it until 0.5.0.
